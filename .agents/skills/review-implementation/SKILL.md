# 実装レビュー

実装の説明とコードレビューを行い、1枚の静的HTMLへまとめる。問題を発見しても、
別途依頼されるまでは実装を修正しない。

## 1. レビュー範囲を確定する

1. 作業開始時のコミットSHAを会話、計画、作業記録から特定する。
2. 特定できなければユーザーへ基準コミットを1つだけ質問する。`HEAD~1`などを
   推測で選ばない。
3. 基準コミットから現在までを対象とし、途中のコミット、未コミット変更、
   untrackedファイルを含める。
4. `git diff --name-status`、`git status --short`、untrackedファイル一覧を先に取得する。
5. `.env*`、`*credentials*`、`*secret*`、`*.pem`、`*.key`などを機密候補として
   分類し、内容や差分を読まない。
6. 機密候補以外の`git diff`と必要なファイル本文を読み、変更の意図と影響を把握する。
7. リポジトリの`AGENTS.md`と参照先ルールを読み、レビュー基準に含める。

## 2. 検証とレビューを行う

1. `.agents/docs.md`に従って`mise run verify`を実行する。
2. 検証が失敗してもレポート作成を続け、失敗理由と未検証範囲を記録する。
3. 人が編集した意味のある変更ファイルを1つずつレビューする。
4. lockfile、生成物、バイナリは変更概要だけを記録する。
5. `.env`、認証情報、秘密鍵、トークンなどは内容を掲載せず、機密情報のため
   非表示にしたことだけを記録する。

各ファイルには次を記載する。

- 変更内容の1行説明
- 理解に必要な場合だけ、詳細説明と重要箇所のコード抜粋
- 実質的または参考になる指摘がある場合だけ、レビューコメント
- 指摘がない場合は「レビュー指摘なし」

差分全文や固定数の抜粋を載せない。説明または指摘に必要なコードだけを選び、
省略が誤解を招く場合は省略したことを明記する。

レビューコメントには対象行、理由、影響、具体的な改善案を含め、次の重要度を使う。

- `Critical`: 修正必須の重大問題
- `Warning`: バグや保守性悪化につながる修正推奨事項
- `Suggestion`: より良くするための提案
- `Optional`: 好み、軽微な改善、どちらでもよい指摘

総合判定は次のいずれかにする。

- `approve`: 重大な問題なし
- `approve-with-suggestions`: 任意または推奨の改善あり
- `changes-requested`: 修正すべき問題あり

## 3. HTMLを生成する

1. レビュー結果をUTF-8のJSONオブジェクトへまとめ、`title`には変更全体を表す
   PRタイトル相当の短い名前を設定する。
2. JSON形式は`scripts/render_review.py --print-schema`で確認する。
3. 一時JSONは`.agents/review/`以外へ置くか、HTML生成後に残さない。
4. リポジトリルートから次を実行する。

```bash
python3 .agents/skills/review-implementation/scripts/render_review.py \
  --input <review.json>
```

スクリプトは`.agents/review/<日時>-<titleのslug>.html`へ、CSSとJavaScriptを
埋め込んだ自己完結型HTMLを生成する。`title`が空の場合だけブランチ名を使う。
過去のレポートを削除しない。
環境のsandboxが`.agents`への書き込みを拒否した場合は、ユーザーへ承認を求めて
同じコマンドを権限付きで再実行する。別の出力先へ黙って変更しない。

ユーザーがブラウザ表示を明示した場合だけ`--open`を追加する。通常は生成された
HTMLへのクリック可能なリンクを返す。ブラウザを開けなくても生成成功として扱い、
ファイルパスを案内する。

## 4. 完了を報告する

HTMLの絶対パス、総合判定、重要度別の指摘件数、検証結果を簡潔に報告する。
コードを変更していないことも明記する。
