# PR説明の準備

差分を短時間で把握でき、PR上だけで内容を理解できる本文をMarkdownで作成する。
HTMLや説明用の画像は生成せず、見出しと表によって情報を整理する。

## 差分を確認する

1. 既存PRではそのbase branch、新規PRではremoteのdefault branchを基準にする。
2. 基準branchとのmerge-baseからworking treeまでの変更ファイルと差分を確認する。
   PR作成前で未コミットの場合は、今回の実装としてPRへ含めるuntrackedファイルも対象にする。
   ローカル専用の成果物など、PRへ含めるか判断できないファイルは推測で掲載しない。
3. `.env*`、`*credentials*`、`*secret*`、`*.pem`、`*.key`などは内容を読まず、
   機密候補が含まれることだけを報告する。
4. 生成物、lockfile、バイナリは必要以上に展開せず、変更理由が分かる範囲で扱う。

## 本文を書く

リポジトリのPRテンプレートを優先し、次を必ず含める。

### 概要

- 変更の目的と結果を1〜2文で説明する。
- ファイル名や実装手順の列挙ではなく、利用者またはシステムに何が変わるかを書く。
- 前置き、自己評価、レビュー判定、差分から確認できない効果は書かない。

### 変更ファイル

- Markdown表へ、PRに含まれる全変更ファイルを1行ずつ記載する。
- 列は`ファイル`と`変更`だけにする。
- `変更`は改行のない1文とし、そのファイルの役割と今回変えたことが同時に分かる表現にする。
- 追加、削除、移動が理解に必要な場合は明記する。
- 同じ説明を複数行へコピーせず、各ファイル固有の差分を書く。

```md
## 概要

記事編集画面から画像をアップロードし、Markdownへ挿入できるようにしました。

## 変更ファイル

| ファイル | 変更 |
| --- | --- |
| `src/app/example.tsx` | 画像選択とアップロード結果の挿入操作を追加 |
| `src/app/api/example/route.ts` | 画像アップロードAPIを追加 |
```

### 視覚的な確認

- UIの見た目、レイアウト、レスポンシブ動作が変わる場合だけ追加する。
- 変更結果を最もよく表す実画面のスクリーンショットを最大1枚に絞る。
- 画像だけに情報を閉じ込めず、短い代替テキストを付ける。
- PR閲覧者が参照できる永続URLがない画像や、ローカルファイルへのリンクは掲載しない。
- UI変更がない場合は、このセクション自体を省略する。説明用HTML、装飾画像、
  差分を画像化したものは作らない。

### 検証と関連情報

- 実行した検証と結果を短く記載する。失敗または未実行なら理由も書く。
- Issueなど既知の関連情報がある場合だけ記載し、空の項目は残さない。
- リポジトリのPRテンプレートに必須項目があれば、省略せず簡潔に埋める。

## PRへ反映する

PRの作成または更新を依頼されている場合は、生成した本文をその操作へ使用する。
本文の準備だけを依頼されている場合は、PRを作成・更新せずMarkdownを提示する。

詳細なコードレビューやHTMLレポートも依頼された場合は、PR本文とは分離して
`review-implementation`を使用する。
